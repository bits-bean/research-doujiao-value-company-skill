# 可选的商业闭环与正反馈机制

研究商业模式时，先完成参与者与价值交换，再判断是否有值得单独解释的商业闭环。本文件所称闭环，是一个经营变化沿有证据的因果链传导，最终反过来增强起点的机制。交易被公司称为“闭环网络”、付款与交付能画成圈，或价值创造、传递、回收三个环节齐全，都不能单独证明存在这种正反馈。

## 是否展示

- 仅在完整机制得到足够支持时展示；完整性包括最后一环为什么会反馈到起点。区分已披露事实、管理层因果主张与研究推断；管理层画出的飞轮也需要挑战，经营指标同时增长不等于识别了因果。
- 未识别到、业务不适用或证据不足时可以不展示。记录具体原因，不把“尚未建立证据”写成“确定不存在”；不因为缺少闭环降低公司质量判断或阻断其他已完成研究。
- 不以数据、会员补贴、规模效应或平台网络作为统一模板。规模与成本、供给与需求、信任与复购、渠道密度与服务效率等只是检索线索；每家公司的状态、因果环节、长度与机制由实际证据决定。
- 保留原参与者交换图。闭环中的节点表达可变化的经营状态，如使用意愿、交易频率或单位服务成本，而不是再次把公司、顾客、供应商围成一圈。仅有线性价值链时就展示线性关系，不补一条虚构回程线。

## 逐环研究与挑战

先将每个状态写清，说明增加、改善或下降的具体对象，再逐条问“为什么这个变化会推动下一个变化”。因果边可引用原交换图作为业务基础，但不能把一条交易边直接当作因果证明；不是每条因果边都必须对应一笔商品、资金或数据交换。

每一环保留直接来源和精确定位、证据性质、作用机制、适用条件及可能失效的原因。跨期滞后、容量上限、竞争反应、补贴退坡、单位经济性、资本与风险约束按重要性说明，不要求来源未支持的数字或统一指标。推断环节必须明确成立条件和反证/断裂条件，且在面向读者的说明中标出；资料不足以支持关键回程时，整条候选链不作为已成立闭环展示。

尤其检查“数量增长 → 收入 → 利润/现金 → 再投资 → 更好体验”中的跳步：收入不等于利润，利润不等于可自由再投入的现金；再投入是受回报、资本及管理决策约束的资源配置，不会自动发生。网络效应、闭环、护城河和投资吸引力是不同判断，不能互相替代。

独立审查重新核对每条因果边，主动寻找反向因果、共同外部原因和负向反馈，并核实最后一环确实增强起点。给出最弱环节及闭环何时会减弱、停止或反转。不要使用“必然”“离不开”“无限增强”等超出来源支持的绝对措辞，也不把改善某个业务环节等同于公司必然增利。

## 结构化交接

在证据台账顶层可选保存 `business_model_feedback`，与 `business_model` 的参与者/交换边分开；不修改锁定的 `company.json` Schema，不把状态塞进 `actors`、把因果推断伪装成 `flows`。

| 字段 | 契约 |
|---|---|
| `version` | `"1.0"` |
| `status` | `supported` 或 `not_established` |
| `reason` | 为何足以展示，或为何不展示；非空文字，说明取证边界 |
| `loops` | `supported` 时至少一项；`not_established` 时为 `[]` |

每项 `loops[]` 含：

| 字段 | 契约 |
|---|---|
| `id / title` | 唯一语义 ID；当前机制的具体中文标题 |
| `states[]` | 至少两个不同状态，各含 `id / label / definition`；可选 `actor_ids` 引用原交换图参与者 |
| `links[]` | 各含 `id / source / target / mechanism / evidence_type / source_ids / source_locations / conditions / break_conditions`；可选 `flow_ids` 引用原交换图关系 |
| `review` | `pass_id / mechanism_sha256 / verdict / conclusion`，绑定实际完成的隔离审查及具体结论 |

ID 使用现有最多64字符的小写 slug 规则。每条因果边指向两个不同的有效状态；单个机制的每个状态恰有一条入边和一条出边，全部状态构成同一有向环；`links` 按环的遍历顺序保存，起点可任选。最后一环与其他环节接受同等取证。复杂机制可以拆成几条有解释价值的闭环，共享经济事实但各自完整；不按固定数量补节点或拆成多张没有价值的图。

`evidence_type` 为 `fact / management_claim / inference`，分别表示由事实支持的机制、管理层因果主张及研究推断，不代表自动完成了因果识别。`source_ids` 为同包有效来源的非空、不重复数组；`source_locations` 必须逐个以来源 ID 为键，保存实际页码或章节。`conditions / break_conditions` 为非空文字组成的数组；推断边两者至少各一项，其他边可为空，但适用的重要条件仍须在独立审查与读者说明中保留。可选参与者/交换边引用若存在必须有效，不用引用数量衡量机制可信度。

审查须是本包已完成的隔离 `adversarial_review` 或 `source_audit`，执行者与主研究不同，并实际访问该机制引用的全部来源。`mechanism_sha256` 对本条 loop 去掉 `review` 后的整个对象按 UTF-8 JSON（`ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False`）求 SHA-256。`review.verdict` 为 `pending / accepted / requires_revision`；正式展示须为 `accepted`，审查执行完成不等于同意该机制。机制修订后重做相关关闭审查；不能用旧结论批准新链。草稿保留 `review.pass_id:null`、`verdict:pending` 与待审说明，不能伪造审查以通过正式校验。

没有该可选字段，或明确 `not_established` 且 `loops:[]`，均不产生缺失错误或冻结警告；已经声明但结构损坏的内容仍应报错。未完成取证的候选可以留在工作底稿，正式交接选择不展示并说明原因，不能把候选强标为 `supported`。机械校验仅证明结构闭合、引用有效和审查绑定，不能证明商业因果成立。

## 读者表达与下游边界

报告在商业模式的价值交换解释附近，用一段有来源的机制链及关键限制说明有依据的闭环；不适用时无须新增空小节。网站和内容层可把同一冻结机制作为独立的“商业闭环”解释，与参与者关系图相邻呈现，不替代或遮蔽其中的完整关系。不指定固定五步、圆环形状、颜色或像素，不照搬某家公司的图。

下游仅在 `supported` 时展示已审查机制；缺失或 `not_established` 时不画环、不留空卡，也不影响正常关系图。展示必须保留方向、最后回程、重要成立/失效条件及管理层主张/推断标识，不能把“支持收入”缩写成“利润必然增加”。网站尚不支持时记录交接展示缺口；研究层不调用渲染器，也不把交接完成称为网页已更新。

## 行为验证

用独立材料覆盖：有据的非数据正反馈、只有付款与交付的普通交易、缺少最后回程证据的线性改善、包含管理层主张或推断的机制。检查不适用案例能正常结束且不生成空环；检查缺回程、无来源、失效条件被删、旧审查摘要及两个不相连的小环不能冒充一条完整机制。案例只是检验规则，不是所有公司必须套用的闭环类别。
