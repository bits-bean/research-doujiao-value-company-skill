# 商业模式中的具体对象与价值交换

研究“价值如何创造、传递与回收”时读取本文件。图中的对象、名称、数量、插图语义和连接关系都来自当前公司的生意，不能先画通用四角模板再填公司名。

## 先确定研究范围，再找参与者

完整性指在已明确的商业范围内，把影响价值创造、交付、回收及其成立条件的重要参与者和关系交代清楚。先读业务与收入说明、合同和渠道安排，再与成本/供给、经营驱动、护城河和重大风险交叉核对；不能只从收入分部名称找对象，也不能从已经画好的图反生成一份“完整”清单。

从实际使用者、受益者、付款者和交付方分别向外追踪：谁提供必要投入、资产或权利，谁承担履约或损失，谁控制渠道或准入，谁取得收益。角色只是取证线索，不是必填节点表。员工、供应商、资方、监管者等仅在其关系对本图解释有实质影响时纳入，不能因为存在这些群体就全部画上；不同角色也不能为了固定节点数而合并。

以是否会改变读者对赚钱方式、交付依赖、风险承担或优势来源的理解决定重要性。对取证中发现但拟省略、合并或尚不明确的对象，保留原因。来源暂未披露不等于关系不存在；影响核心解释的缺口标为待核实，不能通过删除候选掩盖。

## 关系类型由生意决定

逐条问“谁向谁交付、授予、使用、承担或承诺什么”，用具体动作与标的命名。下表是开放的检索线索，不是枚举，也不要求每家公司具备每一类关系：

| 可能需要研究的关系 | 要辨清的经济含义 |
|---|---|
| 商品、原料、内容、劳务、技术或运营服务 | 谁生产、谁交付、谁使用；商品交付与款项结算可以经过不同主体 |
| 款项、资本、资产、股权或收益分配 | 消费支付、收入、代收结算、融资和利润分配分别指向谁；资产出售与租赁使用权不能混同 |
| 数据、信息、反馈、流量或注意力 | 从哪里形成、由谁取得、用途和作用对象是什么；流量、注意力与可访问的用户数据不是同一回事 |
| 使用权、知识产权、牌照、准入或控制权 | 授予什么权利、使用范围及对应许可费/分成；合作不自动等于授权或数据共享 |
| 风险承担、保险保障、担保、抵押或履约责任 | 谁对谁承担何种义务，何时触发；风险承担不等于风险已经发生或现金已经支付 |
| 公司特有的其他关系 | 用来源支持的具体语义命名，不强塞入上述类别，也不写成空泛的“提供价值” |

条件性责任及款项在可见标签中保留触发条件，不能只藏在图注，也不能暗示本期已经支付。同一对参与者可有多个方向、多个标的的关系；付款不能替代服务、授权或责任连线。一条线只在来源支持同一方向、同一机制时概括多个紧密相关项目。交易、余额、存量权利、条件性承诺及因果影响分别解释，不把它们都画成会计上守恒的流量。信任、品牌和网络效应通常是关系产生的结果；应说明形成机制，不因为正文出现这些词就虚构可转让的“信任流”。

每个已纳入参与者都从“提供/承担什么、获得什么、依赖谁”三个方向检查，并检查参与者之间不经过公司的交易。没有对等交换或反馈的证据时允许单向关系；不能为好看补成双向箭头。间接销售需跟到最终使用者，免费使用者与实际付款者、履约方与结算方要分别表达。

## 取证与命名

- 依据已实际打开的官方业务介绍、销售模式、合同收入、采购及合作安排，识别使用者、实际付款方、产品或服务的交付方、销售渠道和必要的供给方。只纳入解释主要价值交换所需的对象，不按固定数量凑齐角色。
- 图上直接使用具体身份或产品名称。不能把“客户”“产品与渠道”“生态伙伴”“公司”等分类标题当作最终对象名；公司节点使用当前公司名称。相同公司可以有多类使用者与付款方，同一人也可能以不同交易身份参与，须说明区分依据。
- 免费使用者不自动等于付款客户；广告主、平台商户与消费者的款项分别指向真实收款方。经销商收取的零售款不能画成上市公司直接收入；合作分成、采购支出不能画成收入。合作关系也不证明必然有数据回流。
- 每条连线写清真实方向及具体交换/承担标的。`exchange_type` 保存开放的经济语义，不能只填“资金 / 价值 / 数据”三类总称。`kind` 是现有绘图接口的兼容显示分组，不是研究关系的穷举；具体商品、权利、注意力、责任和其他关系都须在 `exchange_type` 与可见 `label` 中表达。仅在来源确实支持时画数据反馈，不为闭环造型补造关系。
- 每个对象和每条关系都绑定同一研究包中的 `source_ids`；证据台账或报告保存业务段落的精确来源定位。经营事实与研究概括分开，未披露的交易机制留作明确限制，不让网站自行研究或补写。

## 从关系解释价值机制

沿实际关系说明：必要投入如何组合成价值，价值如何到达使用者或受益者，公司为何能取得收入、分成、剩余收益或其他可验证的回报。三个环节可以共享关系，但不能只列三句通用口号。与报告中的每项主要收入来源、关键交付依赖和已声称的优势机制交叉核对，发现正文有机制、图中却只有付款或服务时返回补证/补图。

涉及数据优势时，逐段核实“信息来源 → 取得及使用机制 → 作用对象/服务”，必要时分别画多个来源的回传；不能用公司节点的一句“数据优势”代替已证实的关系。授权、规模、网络效应、风险分担或资产运营等优势也使用其实际机制，不能一律套成数据飞轮。未披露的效果不量化，推断与已披露事实分开表述。

独立审查先拿业务证据与报告重新列参与者和关系，再与图及覆盖清单比较，重点找“双方都没写进清单”的遗漏。审查逐项判断省略/合并是否合理、方向及标的是否准确，并核对价值机制。结构校验只证明清单和图一致，不能证明真实商业世界已被穷尽。

判断可选的商业闭环时另读 [business-model-feedback.md](business-model-feedback.md)。参与者交换图负责说明实际关系，闭环负责解释有证据的因果反馈；缺少可靠闭环时保留正常关系图即可。

## 冻结交接

在 `evidence-ledger.json.business_model` 保存专用图谱，随证据台账进入同一 v2 冻结清单。对象与关系的精确来源定位可保存在同台账的 `business_model_source_review`，逐项指回对象 / 关系 ID、来源 ID 与原件段落。不扩展锁定的 `company.json` Schema，不把图谱塞进收入 `segments`、行业指标或计算金额字段。

| 字段 | 契约 |
|---|---|
| `version` | 固定 `"1.0"` |
| `period` | 与 `company.json.income_statement_sankey.fiscal_year` 相同的 `FY` 加四位年份字符串，如 `FY2025` |
| `company_identity` | `company_name_en / ticker / exchange` 与该包 `meta` 精确一致 |
| `actors[]` | `id / label / label_en / detail / detail_en / illustration / source_ids`；可选 `official_logos` 见下文 |
| `flows[]` | `id / source / target / label / label_en / exchange_type / kind / source_ids` |
| `notes / notes_en` | 字符串，说明业务范围、概括方式、交易身份重叠或未覆盖的次要业务；箭头不是精确会计流量 |

对象及连线 ID 使用小写字母开头、小写字母 / 数字 / 连字符组成的最多 64 字符，分别唯一。恰好一个对象使用 `id: "company"` 和 `illustration: "company"`；其他对象 ID 由实际语义命名。每条关系的起终点必须存在且不同，每个对象至少参与一条关系；整图与公司节点连通。

`exchange_type` 是非空开放字符串，例如“商品交付”“专利使用权”“广告触达”“承保责任”“运营控制权”，可按当前公司继续新增，不设固定行业模板。`kind` 仍用 `money / value / data` 兼容现有网站：现金收付及融资用 `money`，实际信息/数据交接用 `data`，其他有据的非现金关系暂用 `value` 显示样式；这不把风险或责任定义成收益，也不把注意力改写成数据。可见标签必须保留具体类型和动作，不能只写“价值”。若旧显示方式会误解关系，明确交接展示缺口，由下游扩展图例/样式，不能删除关系或更改其事实来适配三色。每个 `source_ids` 为非空、不重复的有效来源 ID 数组。

### 关系覆盖清单

新正式包另在证据台账顶层保存 `business_model_coverage`，与 `business_model` 同时冻结。它是取证形成的候选清单及裁决，不是绘图后的边列表副本；不扩展 `company.json` Schema。结构如下：

| 字段 | 内容与检查 |
|---|---|
| `version / scope` | `"1.0"`；说明当前业务范围、重要性与拆分边界 |
| `participants[]` | `id / label / disposition / actor_id / reason / source_ids / source_locations` |
| `relationships[]` | `id / source / target / exchange_type / disposition / flow_id / reason / source_ids / source_locations` |
| `value_logic[]` | 三项，`stage` 分别为 `creation / delivery / capture`；每项含 `explanation / flow_ids / source_ids` |
| `review` | `pass_id / graph_sha256 / conclusion`；绑定已实际完成的隔离对抗或来源审查及其具体结论 |

参与者 `id` 是候选身份 ID，`actor_id` 是图中对象 ID，两者可以不同。`disposition` 为 `included / aggregated / excluded / unresolved`：前两种映射有效图中对象，后两种必须为 `actor_id:null`。所有图中对象都要有映射；多个候选合并为一个对象需逐项给理由，不能把付款机制、权利责任不同的身份压成一个通用角色。

关系 `source / target` 指向清单中的两个不同候选参与者。`disposition` 为 `drawn / excluded / unresolved`：`drawn` 绑定实际 `flow_id`，其端点经参与者映射后与图一致，`exchange_type` 也一致；后两种为 `flow_id:null`，保留未画原因。每条图中关系都必须有 `drawn` 项，每条已裁决应画的关系必须出现在图中。不要求所有对象两两连线，也不要求固定数量或固定类型的边。

所有候选项都写 `reason`，区分“存在但不重要”“来源明确否定”与“未有证据支持且不构成核心解释”，不能将三者都概括为“不存在”。只记录取证实际引发的候选，不必罗列所有想象中的关系。`source_locations` 是以 `source_ids` 为键、精确页码或章节为值的对象，键集合与该项来源一致。省略次要关系须说明为何不影响核心解释及其依据；缺证的重要关系使用 `unresolved` 并保留检索依据，阻断新的正式冻结，不能伪装为 `excluded`。重要性的判断沿用本文件开头的标准：只有可能改变赚钱方式、关键交付、风险承担或优势解释的待核实项才阻断正式交接；次要且不影响已陈述机制的未知细节可记录为有理由的范围限制，不能通过缩小范围隐去主要业务。完整性声明不能只用一个 `complete:true` 代替这些记录。

`value_logic.flow_ids` 用图中 `business_model.flows[].id`（不是候选关系 ID）解释三个环节，每项至少引用一条有效关系及来源。数据回流、授权或风险机制的经济作用可在这里详述，图中 `notes` 使用面向读者的简洁版本。完整取证边界与审查记录留在台账，避免把机械字段或大段流程说明塞进图注。

`review.pass_id` 必须解析到本包 `run.passes` 中真实完成、与主研究隔离的 `adversarial_review` 或 `source_audit`；不能用主研究/综合自证；该审查须声明已访问清单及价值机制引用的全部来源。`graph_sha256` 为整个 `business_model` 的 UTF-8 JSON 摘要，使用 `ensure_ascii=False, sort_keys=True, separators=(",", ":")`。改对象、关系、类型或说明后重做对应关闭审查并更新摘要；旧图的审查不能自动批准新图。

局部修订和草稿可如实使用 `review.pass_id:null`，在结论中写明待审及未决问题；这是待完成状态，正式验证仍应报错。不能为通过校验编造审查，也不因局部图谱任务扩展到未请求的完整财务研究或冻结。

### 历史兼容

保留图谱 `version:"1.0"`，新增开放语义与覆盖清单供新研究使用，现有网站仍能读取原有图字段和完整标签。新 `full / incremental` 缺少这些交接记录应报错。历史包仅以 `audit` 检查时，完全缺失的新记录报告“未按新关系完整性契约复核”的警告；已经声明但损坏的记录仍报错。旧冻结文件与其原信任锁保持不变，不因升级 Skill 原地改写，也不把新校验直接套到旧锁后声称历史包合格；需要补齐时创建新版本，重新核证、验证和冻结。

`label` 是简洁中文图上名称，`detail` 补充该对象在当前生意中的身份或作用；英文对应字段表达相同意思。对象数量可随公司变化，不能把不同付款机制的身份合成一个空泛标签以迁就布局。

`illustration` 表达对象的可视语义，使用当前下游图例库的键：`company / cardholder / merchant / travel / gamer / advertiser / cloud / creator / distributor / consumer / supplier / search-user / developer / bank / social-user / digital-buyer / search-distribution / participant`。研究层选择与实际角色相符的语义，实际 SVG、来源许可与布局由网站或内容层管理；同一种真实角色可以复用同一图例，不能按“左上 / 右上 / 右下”位置固定套用三张图。没有准确插图时使用 `participant` 中性文字节点，保留具体名称、身份说明及全部关系；它不表示一种经济角色，也不生成或猜测插图。这个明确的后备键需要下游解析器和渲染器支持，不能把任意未知键静默降级。可后续为已明确的角色补充合适图例，不借用含义不符的插图，也不能因图库缺项删掉参与者或阻断语义研究。

### 品牌与产品的官方标识

实际对象涉及官方业务资料已确认的品牌或产品时，优先交接其官方标识引用；没有对应品牌身份或下游无法取得已核验官方原件时，保留 `illustration` 作为后备。不能仅因研究对象是一家公司，就给普通消费者、经销商、广告主、供应商或其他泛指人群添加某个品牌；品牌必须对应这组对象实际使用、购买或提供的产品与服务，来源须支持这一关系。

非公司对象可添加 `official_logos` 数组；省略或 `[]` 均保持原有插图行为，图谱仍为 `version: "1.0"`。每项只含：

| 字段 | 契约 |
|---|---|
| `asset_id` | 下游受控品牌资产库的稳定键；使用与对象 ID 相同的最多 64 字符小写 slug 规则，在同一对象内唯一。它不是 URL、文件路径或图片内容。 |
| `brand_name` | 官方品牌或产品的准确名称，非空字符串；不代替角色名称。 |
| `brand_name_en` | 对应的官方英文名称，非空字符串；英文页面使用它说明同一品牌或产品。 |
| `source_ids` | 同一 `company.json.sources` 中非空、不重复的有效来源 ID，证明该品牌或产品与当前对象的对应关系。 |

同一对象实际涵盖多个品牌或产品时按顺序逐项列出，下游应展示全部标识，不能只保留第一项。继续保留原有 `label / label_en / detail / detail_en`，让标识与“谁使用、谁付款、谁合作”的角色说明共同出现；不能把使用某产品的人群改画成该产品公司本身。公司节点继续使用 `company.json.brand_identity.company_logo`，不通过 `official_logos` 替换公司标识。

`asset_id` 的官方出处、原件 URL、本地文件、SHA-256、格式、取得时间和使用依据由下游资产库记录并核验；研究层只保存品牌与对象的有据对应，不在台账嵌入图片、路径、`data:` URI 或资产下载流程。来源 ID 证明业务关系，不代替官方素材出处核验。下游按 `asset_id` 查找已核验原件，不按公司名、股票代码或对象 ID 猜测品牌；任一声明的标识未取得或未核验时，整个对象回退原角色插图并保留完整角色名称，不静默展示不完整的品牌集合，不使用第三方近似标识、重绘图或其他品牌顶替。

只修改品牌引用也会改变证据台账的冻结字节，须在新版本目录记录修订范围、复核品牌对应关系并重新验证、冻结。若经营事实和计算未变，保留其原值与原有审计时间，说明本次只补品牌身份交接；不为视觉修订刷新数据日、估值日或声称重新完成人工审核。实际素材留在研究冻结包外。

报告商业模式章节用通俗文字解释主要对象与交易关系，机器字段和图例键只留在证据台账与完整度说明。图谱新增事实执行相应来源复核；仅把已审阅事实组织成图谱时，记录对应段落、来源和关系方向的复核，不改写财务、估值或投资判断。

## 验证与网页消费

新完整研究、修复或增量交接须提供图谱及关系覆盖清单。验证器检查身份、期间、来源解析、具体命名、唯一 ID、连接引用、连通性、开放关系类型、图例语义键、可选品牌引用，以及清单与图逐项对账、未决项、价值机制引用和审查摘要。历史包缺少记录只能作兼容审查。经济重要性、遗漏候选、来源支持程度及合并是否合理仍须独立语义复核，结构通过不等于事实正确或关系已经完整。

网站与导出器从同一版本的证据台账读取对象、连线和可选品牌引用，优先使用匹配的已核验官方标识，其他对象按具体 `illustration` 配置有来源和许可的图例；公司节点使用已验证公司标识。布局根据实际对象数量和连接方向安排，名称在宽窄屏均应清晰可读。复杂关系可以由下游分组、分层或提供局部视图，但必须保留完整关系及清楚的索引，不能用隐藏边、改变端点或合并不同机制来换取整齐。研究层交接语义与完整性记录，不设像素坐标、不调用渲染器。已有有效图谱时不得回落到通用角色或按行业、股票代码猜测对象；身份错配、来源缺失或连接无效时应明确显示数据缺口。

验收使用不同生意的独立案例：无数据反馈的生产与分销、免费使用者和广告付款方分离、授权与分成、保障责任与条件赔付，以及当前公司新增的其他关系。案例种类是评估覆盖，不是给公司套模板。还应测试：删除关系而图仍连通、遗漏间接交易、反向箭头、把风险当现金、以普通“价值”吞掉不同权利，以及新自定义关系类型。逐条核对名称、插图、方向、语义和来源；名称或图例没有变而仅换公司标识，不算完成跨公司适配。
