# 财报监控与增量研究规范

本文件定义公司研究完成后的财报监控、增量研究、冻结与授权 GitHub 交付。网站渲染和内容生产属于下游，不在本流程执行。

## 1. 目标
对于已经完成研究并拥有 `companies/<company-slug>/company.json` 的公司，持续识别新财报或重大官方披露，在新信息出现时更新研究数据，而不是每次从零重做。

## 2. 监控对象
优先监控：
1. 公司 Investor Relations；
2. 交易所/监管披露；
3. SEC EDGAR、港交所披露易或相应官方系统；
4. 官方 earnings release；
5. 官方投资者演示；
6. 官方业绩会资料。

媒体报道不能单独作为“财报已发布”的确认依据。

## 3. reporting 字段
`company.json` 的 `reporting` 模块应维护：
- latest_report；
- 报告对应期间；
- 官方发布日期；
- next_expected_report；
- 日期是否官方确认；
- 最近检查日期；
- 相关 source_ids。

预计日期必须区分：
- 官方确认；
- 按历史节奏估算。

非官方日期不得标记为 confirmed。

## 4. 初次研究完成后的动作
完成公司首次研究后：
1. 保存最新完整财报与最新季度信息；
2. 确定下一次可能财报期间；
3. 查询公司是否已经公布正式日期；
4. 若没有，按历史披露节奏给出预计窗口并降低确定性；
5. 写入 `reporting`；
6. 将后续监控范围限定在官方来源。

## 5. 新财报触发条件
只有发现比 `reporting.latest_report` 更新、且可以由官方来源确认的新财报/业绩公告时，才启动财报更新。

避免因为：
- 媒体预告；
- 分析师预测；
- 市场传闻；
- 重复转载；
- 同一财报的不同链接

重复触发。

## 6. 增量更新流程
触发后：
1. 读取当前研究 Skill 信任锁绑定的 `references/specs/company.schema.json` 只读副本；若 `doujiao-value-system` 权威 Schema 已变化，先更新并发布新版 Skill，不在本次更新中静默切换；
2. 读取现有 `companies/<company-slug>/company.json`；若它属于旧 Schema 并使用千、百万或十亿缩放值，不得原地覆盖或直接与当前数值混算，应按旧 manifest 锁定的 Schema 解释后，在新的版本目录中机械换算为实际原始数值并重新校验、冻结；
3. 获取新财报、业绩公告、投资者演示与业绩会；
4. 建立“旧数据 vs 新数据”差异；
5. 更新最新季度/半年度/年度数据；
6. 重新计算近12个月（TTM）；
7. 更新受影响的 `classification`、`financials`、`industry_metrics`、`durability`、segments、capital_allocation、buyback_ledger、debt_maturities 等；监管身份或主营经济来源发生变化时重新审定两个路由字段，不能根据新增指标自动换模板；长期生存三维判断只有在新证据改变状态、证据或破坏条件时才更新；
8. 重新检查 FCF、Owner Earnings、ROIC 与股份变化；
9. 检查商业模式、护城河、管理层承诺的下一验证、资本配置结果、风险因果链和长期跟踪方法是否出现结构性变化；
10. 更新估值与 verdict；
11. 更新 `meta.data_as_of` 和 `meta.valuation_date`；
12. 更新 `reporting.latest_report`；
13. 计算或查询下一次预计财报；
14. 校验完整 `company.json`；
15. 重新验证、冻结同一版本的报告、`company.json`、证据台账和计算台账；
16. 用户明确授权时，把冻结研究包及按身份素材契约验证的缺失素材原子提交到 `doujiao-value-system/companies/<slug>/`；随后停止，不调用网站、图表或内容流程。

## 7. 财报解读框架
必须回答：
1. 本次最重要的变化是什么？
2. 哪些只是短期季度噪音？
3. 哪些可能具有长期意义？
4. 核心商业模式是否改变？
5. 护城河增强、稳定还是削弱？
6. 现金创造能力是否改变？
7. 管理层资本配置是否改变？
8. 原关键假设被强化还是削弱？
9. 是否出现新的 thesis breaker？
10. 当前估值是否明显变化？

最终标记长期投资逻辑：
增强 / 基本不变 / 削弱 / 被推翻 / 暂无法判断。

不得因为单季同比增速或一次利润波动轻易改变长期结论。

## 8. 重大非财报事件
若发生可能改变长期投资逻辑的重大官方事件，也可触发研究更新，例如：
- 大型并购或出售；
- CEO/董事长重大变更；
- 大规模资本重组；
- 重大诉讼或监管处罚；
- 债务危机或重大融资；
- 关键产品停运；
- 会计重述或审计异常。

这类事件应更新受影响字段和研究结论，但不要伪装成财报更新。

## 9. system 交接
system 只接收最终校验并冻结的研究包。GitHub 交付是可选且须获授权；它只更新 `companies/<slug>/` 的研究文件与已验证身份素材，不调用网站 API，不导出图表，不生成 `images/`，也不声称部署成功。

网站和基础图表代码从 `company.json`、台账及来源元数据读取同一冻结事实。若路由字段或图表必需数据缺失，system 应明确缺口或拒绝渲染，不能由本 Skill 或网站猜测补齐。

## 10. 内容层边界
财报内容可以由下游从更新后的冻结包派生，但本 Skill 不自动调用 `$produce-doujiao-value-content`，不加载平台规则，不选择渠道比例、背景、布局或品牌元素位置，不合成图片，也不发布内容。

用户另行调用内容 Skill 时，下游应验证冻结哈希和 Schema 锚点，并统一回答“什么变了、什么没变、长期逻辑是否改变”；不得反向修改研究事实、估值或结论。

## 11. 去重与版本控制
每次更新应以：
- 公司；
- 报告期间；
- 官方发布日期；
- 来源 ID

作为去重基础。

不得因同一财报的多份官方材料重复新增同一期间。

`schema_version` 由当前 Skill 信任锁绑定的 Schema 决定；研究协议版本与 Schema 版本分开管理。权威 Schema 更新后，必须先发布新版研究 Skill 才能用于新的正式冻结。历史冻结包保持不可变，并继续由其 manifest 锁定的旧 Schema 解释；升级研究只能创建新版本，不能静默改写历史数字。

Schema 1.x 包不能直接作为 Schema 2.0 增量链的前序包。先新建迁移目录，从原始来源重建 `classification`、`industry_metrics`、`durability`、承诺验证、资本配置结果、风险因果链和领先指标复查方法，运行 2.0 `full` 验证并冻结；不能只改版本号、复制旧自由文本，也不能由网站、护城河分数或估值字段反推分类与长期生存结论。完成该基线迁移后，后续财报才可按 2.0 incremental 链更新。

## 12. 人工审核
在系统早期阶段，默认采用：
自动发现 / 研究 / 校验 → 人工审核 → 冻结 → 获授权后 GitHub 交付。

研究完成或 GitHub 交付都不等于网站部署、图表导出、渠道图片生成或公开发布。
